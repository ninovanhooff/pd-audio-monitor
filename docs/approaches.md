# Approaches

Goal: let a composer hear their music through the Playdate's own speaker, in the format it will
ship in (default 22.05 kHz mono IMA ADPCM), while still working in their DAW on the Mac.

Facts are from SDK 3.1.2 docs and headers, the SDK changelog, community reverse engineering, and
our own measurements (marked *measured*). **(measure)** marks open questions.

## 1. Line-in monitor (analog), built: `line-in-monitor/`

Mac audio out → TRRS splitter → Playdate headset mic input → format emulation on the device → speaker.

- Panic anticipates this: `setMicCallback(…, kMicInputHeadset)` forces the headset input "if you're
  using a headphone splitter to wire an external source to the mic input" (Inside Playdate with C).
- Input and output share the Playdate's clock, so there's no drift, no transport and no Mac
  software. It works with any source: a DAW, a tracker, a browser, a phone.
- The codec is emulated on the device: decimate → quantize → linear upsample. In the Simulator, the
  device-side chain matches the host `chain_render` to −83 dB (*measured*, `tests/sim_e2e.sh`).
- Costs: the analog path adds the mic preamp's noise and response **(measure)**, and the levels need
  setting (line out vs mic level). Lua can't do this: its mic API only records into fixed-length
  samples, so streaming mic → speaker needs C (`setMicCallback` plus a callback source).

## 2. Digital streaming from the Mac, built: `usb-stream/`

The prototype is BlackHole, then `pdstream.py` (or the PD Audio Monitor Host app), then serial
`eval` commands, then a C receiver (PD Audio Monitor Receiver). The sender and receiver halves of
the chain reproduce `chain_render` bit for bit (host tests), and every format plays on hardware.

Mac captures audio → encodes in the target format → sends it to a receiver app → the receiver
decodes and plays it.

### Capture on macOS

| Option | Composer does | Notes |
| --- | --- | --- |
| AudioServerPlugIn (HAL) virtual device | Picks "Playdate" as the output device | Same tech as BlackHole. Runs inside the sandboxed `coreaudiod`, which can't open serial ports, so it stays a loopback and a companion app handles transport. Signed + notarized `.pkg`; no special entitlement. C/C++: Apple's NullAudio sample or libASPL (MIT). |
| Core Audio process tap (macOS 14.2+) | Picks the DAW in the companion app | `AudioHardwareCreateProcessTap` + `CATapDescription`, and `muteBehavior = .muted` silences it on the Mac. Nothing to install. |
| BlackHole + companion app | Installs BlackHole | No driver work; prototype path. |
| AU/VST master-bus plugin | Inserts a plugin | DAW-only; can also play the codec preview locally. |

### Transport

- **USB serial `msg`.** VID `0x1331`, PID `0x5740` (`/dev/cu.usbmodemPD…`). Messages arrive in
  `playdate->system->setSerialMessageCallback` / `playdate.serialMessageReceived` (SDK 2.4+).
  - The device caps each line at about 251 payload chars. LF ends a message, CR and some control
    characters are dropped, so the payload must be text: base64 carries 186 bytes per message.
    Source: [devforum](https://devforum.play.date/t/msg-command-sim-device-differences-control-codes-dropped-max-length/16443).
  - A Playdate takes about 390 messages/s (*measured*): every format but the 44.1 kHz 16-bit
    bypass (493 messages/s). Not used: `eval` carries every format.
- **USB serial `eval <len>\n<bytes>`.** Takes an arbitrary-length *binary* payload of compiled Lua
  bytecode, and only for sideloaded Lua or C+Lua games. Host-generated bytecode such as
  `feed("<raw bytes>")` gets past the line limit and the base64 overhead. The bytecode must match
  Playdate's Lua 5.4 build (4-byte integers and floats); the host builds it around the payload from
  a pdc-compiled template. The game needs a `main.lua` (an empty one will do) and must set
  any C update callback at `kEventInitLua`: one set at `kEventInit` keeps the Lua runtime from
  starting, and the device then answers "Lua runtime is not available".
  - With 1 KB packets, 86 evals/s carry the bypass (*measured*).
- **Wi-Fi TCP** (SDK 2.7+). The device is client-only and needs a permission prompt. The Mac runs
  the server, and its address can be sent over USB.

### Receiver

Lua alone can't feed PCM to the audio engine: there's no API to write bytes into a sample, so a
receiver would have to go through files and suffer gaps. So the receiver (`usb-stream/receiver`) is
a **C+Lua hybrid**: `eval` bytecode calls a C function from Lua, and C decodes into a ring buffer
played by a callback source. That's the same playback path as the line-in monitor, so
`shared/codec` is reused.

Alternatively, the native ADPCM path: `newSampleFromData(…, kSoundADPCMMono, …)` over a ring of
`.pda`-layout blocks. How the block size reaches it is **(measure)**; `getData()` on a loaded
`.pda` includes the uint16 block size first.

The speaker mixes both channels to mono (SDK 1.13), so stereo only matters on headphones. QOA's rows
count the stream's frames (100, 50 or 25 slices; frame header and LMS state included), which is 3.3 to
3.6 bits per sample; a 256-slice file takes 3.2 plus its headers.

## Codec facts we pinned down

- IMA ADPCM decoders **differ in rounding**. The IMA reference (and Python's `audioop`) adds shifted
  steps, while ffmpeg's `adpcm_ima_wav` multiplies. They diverge by up to about 46 LSB on our test
  signal (*measured*). In the Simulator, Playdate's decoder is shift-add (*measured*); the device
  must match, or it couldn't play the same files.
- `.pda` ADPCM = `Playdate AUD`, 24-bit rate, format byte, uint16 block size, then the WAV's blocks
  with the **nibble order swapped** (high first) (*measured*; `run_tests.sh` checks it with pdc).
- Playing a 22.05 kHz sample uses **linear interpolation** to 44.1 kHz, with no extra filtering
  (Simulator, −90 dB residual, *measured*; the device must match).
- Encoders differ more than decoders. Greedy (Audacity, ffmpeg) vs look-ahead (`adpcm-xq`) is
  audible, so the chain uses the greedy reference encoder, which matches `audioop` bit-for-bit.

## QOA

[QOA](https://qoaformat.org) is a lossy time-domain codec: a four-tap sign-sign LMS filter predicts each
sample and a 3-bit code corrects it, scaled by one of 16 scalefactors per 20-sample slice. The Playdate
doesn't play it: SDK 3.1.2's `SoundFormat` stops at 8/16-bit PCM and ADPCM, and the docs add only MP3.
A game would ship `.qoa` files and decode them with its own C (the reference decoder is about 400
lines), so the QOA formats emulate that, with the system's linear upsampling assumed for the rates
below 44.1 kHz.

- Our encoder writes the same bytes as the reference encoder (phoboslab/qoa `qoa.h`) for the signals
  we tried, including the 32-bit wraparound the reference relies on in its scalefactor division
  (*measured*, `shared/codec/tests/check.py`). Our decoder matches one written from the spec.
- QOA files hold 256 slices per frame (5120 samples: 116 ms at 44.1 kHz, 464 ms at 11.025 kHz). The
  stream uses 100, 50 or 25 slices to keep a unit's length near an ADPCM block's. The LMS state sits in
  every frame header, so the frame length shouldn't change the decoded audio, and on 11 test signals
  (noise, square waves, bursts, silence, sweeps) no sample differed between 256, 100, 50 and 25 slices
  (*measured*; `check.py` compares a stream with a file). A tie between two scalefactors could break it,
  as the reference encoder restarts its search at scalefactor 0 in every frame.
- Digital silence decodes to ±1 LSB (about −92 dBFS, *measured*): no code means zero.
- SNR on synthetic 44.1 kHz signals, against 8-bit and ADPCM (*measured* with `chain_render`):

  | Signal | Level | 8-bit | ADPCM | QOA |
  | --- | --- | --- | --- | --- |
  | Four tones, 50 dB noise floor | −6 dBFS | 38.0 dB | 28.2 dB | 35.9 dB |
  | | −54 dBFS | 0.0 dB | 27.4 dB | 30.2 dB |
  | Smoothed white noise | −6 dBFS | 33.1 dB | 22.9 dB | 21.6 dB |
  | | −54 dBFS | 0.0 dB | 22.6 dB | 14.4 dB |
  | Decaying noise bursts | −6 dBFS | 26.7 dB | 11.9 dB | 15.3 dB |
  | | −54 dBFS | 0.0 dB | 13.6 dB | 9.1 dB |

  QOA is ahead of ADPCM on tonal material and loud bursts, and behind it on quiet noise.
- The encoder tries all 16 scalefactors per slice, stopping a try as soon as it can't win: 2 to 7 trial
  samples per sample on the host. On the device **(measure)**.

## Order of work

1. Run `probes/playback-probe` on hardware. The line-in monitor's input is noisy on hardware,
   worse with USB attached.
2. A macOS companion app (menu bar, format picker, process tap) in place of BlackHole and the script.
   The HAL device comes later.
